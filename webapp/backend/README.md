# Leafy AI Web Backend

The Web Backend is the authenticated gateway between the browser frontend and the Leafy Engine. It is a Node.js/Express service that manages Google sign-in, application sessions, role/permission checks, user administration and authenticated proxy requests to the Engine.

## Architecture

```text
Browser
  |
  | Google credential / web access token
  v
Backend :3000
  |
  +-- backend PostgreSQL database
  |     users, allowed users, permissions, sessions
  |
  | short-lived Ed25519 service JWT
  | trusted X-User-ID / X-User-Role
  v
Engine :8000
  |
  +-- farm database / hardware / AI Core
```

## Tech Stack

- Node.js
- Express 5
- PostgreSQL (`pg`)
- Google Auth Library
- JSON Web Tokens
- Axios
- CORS
- Express Rate Limit

## Authentication

### Google Sign-In

`POST /api/auth/google` accepts the Google credential generated by the frontend. The backend verifies it against `GOOGLE_CLIENT_ID`, checks the application's allowed-user records, synchronizes the local user and creates the Leafy web session/tokens.

The OAuth client ID used by the frontend build must correspond to the backend's configured Google client ID.

For production/LAN clients, Google requires the browser origin to be an authorized Web OAuth origin. A raw private IP such as `https://192.168.x.x` is not a suitable final Google OAuth origin even if the TLS certificate contains that IP.

### Sessions

Authentication routes include:

- `POST /api/auth/google`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `GET /api/auth/me`

Refresh/session state is managed in the backend database.

## Authorization

The backend uses authenticated user information rather than trusting browser-supplied service context.

Current application roles are:

- `OPERATOR`
- `ADMIN`

Feature permissions are stored/configured separately and checked by routes for sensitive operations. Examples include:

- `SCHEDULE_MANAGE`
- `APPROVAL_REVIEW`
- `GROW_CYCLE_MANAGE`
- `HARVEST_RECORD`
- `SETTINGS_MANAGE`
- `EMERGENCY_STOP`
- `CLEAR_EMERGENCY_STOP`
- `AI_TOGGLE`

The frontend may hide unavailable controls, but backend authorization remains authoritative.

## Backend-to-Engine Authentication

The backend signs a short-lived Ed25519 JWT for Engine requests and supplies trusted user context headers derived from the authenticated web user.

Conceptually:

```http
Authorization: Bearer <service-jwt>
X-User-ID: <authenticated user id>
X-User-Role: <authenticated role>
```

The Engine validates the service JWT using the backend public key generated by the Compose `key-init` service.

All farm/application routes are under `/api`.

### Settings

- `GET /api/settings`
- `POST /api/settings/reload`
- `POST /api/settings/reset`
- `PATCH /api/settings`

Settings updates require `SETTINGS_MANAGE`. AI enablement and emergency-stop state are managed through the Safety API rather than normal settings updates.

### Logs

- `GET /api/logs`

Backend-originated audit events are sent to the Engine over the authenticated service connection; the backend does not directly write to the Engine's farm database.

### Administration

Admin routes under `/api/admin` manage allowed users and configurable permissions. They include list/create/update/delete user-access records and list/update permission configuration.

## Health

The backend exposes:

```text
GET /health
```

The Docker health check uses `http://127.0.0.1:3000/health` inside the container.

This confirms the backend process is responding; it should not be interpreted as proof that every Engine/hardware dependency is healthy.

## Running Locally

```bash
cd webapp/backend
npm ci
npm start
```

When running outside Docker, set `ENGINE_URL` to an address reachable from the host process, such as `http://127.0.0.1:8000`. The Docker service hostname `engine` only resolves inside the Compose network.

## Docker

The backend is not published directly to the LAN. Nginx reaches it by Docker DNS:

```text
http://backend:3000
```

The backend reaches the Engine at:

```text
http://engine:8000
```
