# Webapp Backend to Leafy Engine API

The Leafy AI Webapp Backend provides the authenticated API gateway between the React frontend and the Leafy Engine.

The browser authenticates to the Node.js backend using its normal webapp access token. The backend validates the authenticated user, checks the required permissions, and forwards authorized requests to the Leafy Engine using a short-lived Ed25519 service JWT.

The Engine validates the service JWT and receives trusted user context through headers generated by the backend.

## 1. Architecture

```text
React Frontend
    |
    | Webapp access JWT
    v
Node.js Webapp Backend
    |
    | Authentication and RBAC
    | Short-lived Ed25519 service JWT
    | X-User-ID / X-User-Role
    v
Leafy Engine API (FastAPI)
    |
    +-- Farm monitoring and sensor history
    +-- Camera images and vision analysis
    +-- Farm controls
    +-- Scheduled tasks and execution history
    +-- AI recommendations and approvals
    +-- Safety monitoring and emergency controls
    +-- Grow cycles and harvest records
    +-- System settings and audit logs
    |
    v
PostgreSQL Engine Database
```

The Webapp Backend does not connect directly to the Leafy Engine database. Engine-owned operations are performed through the authenticated Engine API.

The backend database is used for web authentication, sessions, users, roles, and related access-management data.

## 2. Required Backend Environment

```env
ENGINE_URL=http://127.0.0.1:8000
ENGINE_TIMEOUT_MS=15000
ENGINE_PRIVATE_KEY_PATH=../../secrets/webapp_backend_private_key
```

When running the backend and Engine in Docker Compose, use the Engine service hostname:

```env
ENGINE_URL=http://engine:8000
```

The Engine must listen on an interface accessible to the backend container, rather than only `127.0.0.1` inside its own container.

The actual Docker Compose service name and container port must match the deployment configuration.

### Generate Service Authentication Keys

Generate the Webapp Backend to Engine Ed25519 key pair:

```bash
npm run generate:engine-keys
```

Configure the Engine to load the corresponding public key:

```env
WEBAPP_BACKEND_PUBLIC_KEY_PATH=/run/secrets/webapp_backend_public_key
```

The private key must remain accessible only to the Webapp Backend.

The Engine receives only the public key needed to verify the backend's service JWTs.

Do not place the private key in the React frontend or expose it through any browser-accessible API.

## 3. Authentication and Authorization

All `/api/*` routes described below require a valid authenticated webapp user unless otherwise explicitly documented.

The backend performs authentication and permission checks before forwarding requests to the Engine.

Authorization is based on the user's authenticated identity, role, and configured permissions.

The system supports role-based access control, including the `ADMIN` and `OPERATOR` roles and configured feature permissions.

### Trusted User Context

The backend forwards authenticated user context to the Engine using:

```http
X-User-ID: <authenticated-user-id>
X-User-Role: <authenticated-user-role>
Authorization: Bearer <short-lived-service-jwt>
```

These headers are generated by the backend.

The backend must not trust browser-supplied `X-User-ID`, `X-User-Role`, or service authorization headers.

The Engine must validate the service JWT before accepting the forwarded user context.

### Permission Enforcement

Sensitive operations require explicit authorization.

Examples include:

- `SCHEDULE_MANAGE` for creating, modifying, enabling, disabling, and deleting schedules.
- `APPROVAL_REVIEW` for reviewing approval requests.
- `GROW_CYCLE_MANAGE` for managing grow cycles.
- `HARVEST_RECORD` for recording harvests.
- Administrative permissions for restricted farm settings and controls.

The Engine also enforces its own authorization and safety checks where applicable.

Frontend visibility controls are not a substitute for backend authorization.

## 4. Farm Monitoring API

These endpoints provide farm state, sensor information, historical readings, and camera data.

| Method | Endpoint                                 | Description                                     |
| ------ | ---------------------------------------- | ----------------------------------------------- |
| GET    | `/api/farm/state`                        | Retrieve overall farm state                     |
| GET    | `/api/farm/sensors`                      | Retrieve configured sensors and latest readings |
| GET    | `/api/farm/sensors/:sensorType/readings` | Retrieve raw historical readings                |
| GET    | `/api/farm/sensors/:sensorType/history`  | Legacy sensor history endpoint, if retained     |
| GET    | `/api/farm/sensors/stream`               | Stream live sensor updates                      |
| GET    | `/api/farm/cameras`                      | Retrieve configured cameras                     |
| GET    | `/api/farm/cameras/:cameraId/image`      | Retrieve the latest captured image              |
| GET    | `/api/farm/cameras/:cameraId/analysis`   | Retrieve camera vision-analysis information     |

### Historical Sensor Readings

The frontend can request sensor readings using a time range:

```http
GET /api/farm/sensors/ph/readings?start_time=2026-10-11T00:00:00Z&end_time=2026-10-11T01:00:00Z
```

The chart can request additional historical data when the user zooms or pans.

Historical readings are retrieved from PostgreSQL without applying the aggregation intended for LLM sensor-analysis tools.

The chart should preserve actual measurement timestamps and numeric values.

The backend may enforce query-range, result-size, and rate limits to protect the database.

### Live Sensor Streaming

```http
GET /api/farm/sensors/stream
```

The frontend uses the sensor stream to receive recent measurements without repeatedly fetching the complete sensor history.

Live measurements and historical database queries serve different purposes.

### Camera Monitoring

The system supports multiple cameras associated with farm levels.

The Monitoring interface displays separate camera cards for Level 1 and Level 2, with navigation between multiple cameras belonging to the same level.

Camera images represent the latest captured image, not a continuous video stream.

## 6. Task Schedule API

The schedule API supports creating, editing, enabling, disabling, and manually deleting scheduled farm tasks.

| Method | Endpoint                                 | Description         |
| ------ | ---------------------------------------- | ------------------- |
| GET    | `/api/farm/schedule`                     | List schedules      |
| GET    | `/api/farm/schedule/:scheduleId`         | Retrieve a schedule |
| POST   | `/api/farm/schedule`                     | Create a schedule   |
| PATCH  | `/api/farm/schedule/:scheduleId`         | Update a schedule   |
| POST   | `/api/farm/schedule/:scheduleId/enable`  | Enable a schedule   |
| POST   | `/api/farm/schedule/:scheduleId/disable` | Disable a schedule  |
| DELETE | `/api/farm/schedule/:scheduleId`         | Delete a schedule   |

### Schedule Deletion

Schedule deletion requires the `SCHEDULE_MANAGE` permission.

Example:

```http
DELETE /api/farm/schedule/15
```

When a schedule is deleted:

1. The backend authenticates the user and checks permission.
2. The backend forwards the request to the Engine.
3. The Engine deletes the schedule from `farm_schedule`.
4. Historical task execution records are retained.
5. The foreign key uses `ON DELETE SET NULL`, preserving execution history.
6. A `SCHEDULE_DELETED` audit event is recorded.
7. The frontend refreshes the schedule list.

The schedule-deletion operation is intended for authorized human users through the Webapp.

It is not exposed as a `DELETE_SCHEDULE` LLM tool.

| GET    | `/api/task-executions/:executionId` | Retrieve execution details      |
| GET    | `/api/task-executions/summary`      | Retrieve execution statistics   |

Example:

```http
GET /api/task-executions?limit=50&offset=0
```

Execution records include available information such as:

- Execution identifier
- Schedule identifier, when the schedule still exists

Execution history remains available even when its associated schedule has been deleted.

## 8. AI Recommendations and Activity

| Method | Endpoint                  | Description                  |
| ------ | ------------------------- | ---------------------------- |
| GET    | `/api/ai/recommendations` | Retrieve AI recommendations  |
| GET    | `/api/ai/activity`        | Retrieve AI activity history |

The recommendations endpoint supports reviewing recommendations generated by Leafy AI.

The activity endpoint provides historical AI-related activity, including available recommendation and task-execution events.

Where supported, query parameters can be used for pagination and filtering.

### Recommendation Review

AI recommendations can be associated with approval requests.

Advisory recommendations use the existing approval workflow for human review.

Approving an advisory recommendation marks it as accepted without automatically performing a farm operation.

Rejecting an advisory recommendation records the rejection.

Recommendations containing protected executable actions remain subject to the existing action-approval and safety mechanisms.

Leafy AI cannot approve or reject its own recommendations.

## 9. Approval API

| Method | Endpoint                             | Description                |
| ------ | ------------------------------------ | -------------------------- |
| GET    | `/api/approvals`                     | Retrieve approval requests |
| GET    | `/api/approvals/:approvalId`         | Retrieve approval details  |
| POST   | `/api/approvals/:approvalId/approve` | Approve a request          |
| POST   | `/api/approvals/:approvalId/reject`  | Reject a request           |

Approval and rejection operations require the `APPROVAL_REVIEW` permission.

### Approval Types

The approval system supports existing protected farm actions and advisory recommendation reviews.

Advisory recommendation reviews use:

```text
RECOMMENDATION_REVIEW
```

The approval record can reference an AI recommendation through `recommendation_id`.

### Approval Behavior

For an advisory recommendation:

```text
PENDING
   |
   +-- Approve --> APPROVED
   |
   +-- Reject  --> REJECTED
```

An approved advisory recommendation is not automatically marked completed.

For executable actions, approval may authorize an operation, but execution must still pass applicable safety and validation checks.

Approval decisions and corresponding recommendation-status updates should occur within the same database transaction.

Harvest records are associated with grow cycles.

The frontend can display:

- Active grow cycle
- Cycle status and start date
- Latest harvest weight
- Total harvested weight
- Harvest record count
- Average harvest weight

### Grow Cycle Deletion

Grow-cycle deletion is a restricted human operation.

Deletion behavior must follow the Engine's configured retention rules for associated harvest, task, and historical records.

Grow-cycle deletion is not exposed as an unrestricted LLM tool.

## 15. Backend Audit Logging

The Webapp Backend does not connect directly to the Leafy Engine PostgreSQL database.

Backend-generated audit events are forwarded through the authenticated Engine service connection:

```http
POST /audit-logs
```

The Engine validates the service JWT and writes the event to its `audit_logs` table.

The Webapp Backend database remains responsible for web authentication and session-related information.

## 16. Error Handling

The backend should preserve appropriate HTTP status codes from Engine operations.

Common responses include:

| Status      | Meaning                                   |
| ----------- | ----------------------------------------- |
| 400         | Invalid request                           |
| 401         | Missing or invalid authentication         |
| 403         | Insufficient permissions                  |
| 404         | Resource not found                        |
| 409         | Conflicting operation                     |
| 422         | Request validation failed                 |
| 429         | Rate limit exceeded                       |
| 500         | Internal server error                     |
| 502/503/504 | Upstream service unavailable or timed out |

The backend must not expose service private keys, internal credentials, or sensitive exception details to the browser.

When deployed using Docker Compose:

```text

    |
    v
webapp-backend
    |
    | Ed25519 service JWT
    v
engine
    |
    v

```

Use Docker service names for internal communication.

Example:

```env

```

Keep service private keys outside the frontend and supply them to the appropriate containers through protected files or Docker secrets.

The Engine must have access to the Webapp Backend's public key for JWT verification.

The Engine and AI Core may run in separate containers while sharing the necessary internal services.

## 18. Security Principles

The Webapp-to-Engine communication follows these principles:

1. The browser authenticates only to the Webapp Backend.
2. The backend validates user identity and permissions.
3. The backend generates short-lived Ed25519 service JWTs.
4. The Engine verifies the service JWT.
5. User-context headers are generated by the backend, not trusted from the browser.
6. Sensitive farm operations require explicit authorization.
7. Safety restrictions remain enforced in the Engine.
8. AI recommendation approval remains a human-authorized operation.
9. Schedule deletion is not available to the LLM.
10. Engine audit events are retained in the Engine database.
11. Private signing keys are never exposed to the frontend.
12. Internal service access should be restricted through Docker networking and production firewall policies.
